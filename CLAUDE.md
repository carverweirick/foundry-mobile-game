## Currently built

**Project setup**
- `autoload/game_data.gd` registered as the `GameData` autoload singleton.
- `res://scenes/main.tscn` is the main scene.
- `project.godot`: renderer is Vulkan (the D3D12 backend this project briefly used caused mouse input to silently stop reaching the game on at least one dev machine); `window/size/viewport_width`/`viewport_height` are explicitly 480x270 with `stretch/aspect="keep"` (previously unset, which meant the game was actually running at Godot's much larger default base resolution instead of the scale the whole floor layout assumes).

**UI theme** (`resources/theme/ui_theme.tres`, design doc Section 16)
- One shared `Theme` resource, applied project-wide via `project.godot`'s `[gui] theme/custom` rather than assigned per-scene - this is what makes it reach the Station Detail Menu, Menu overlay, and Shop overlay, plus the floor's own labels (station name/status, the HUD currency label, room name labels) automatically, matching Section 16's "keeping the retro feel consistent everywhere, not just on the shop floor itself" instruction literally, without needing to touch every scene's node tree.
- `assets/fonts/m5x7.ttf` (the pixel font added this session) is the theme's `default_font`, `default_font_size = 16`.
- Palette pulled from Section 16's room palettes rather than invented fresh: a warm tan/parchment base (close to the Shelling Room's dusty tan) for panel and button-normal backgrounds, dark near-black brown for every border and body text, the Pour Room's bright yellow-orange as the button-hover/selected-tab accent, and the Furnace Room's ember orange-red as the button-pressed accent - so hovering/pressing a button reads as "heating up," not just a generic color swap.
- All panel/button/tab `StyleBoxFlat`s share the same shape language: sharp corners (`corner_radius_*` = 0), `anti_aliasing = false` for crisp pixel edges, and a chunky border (4px on the outer `Panel`, 3px on buttons/tabs, 2px on `LineEdit`/focus rings). `Button` styles are defined once and cascade to `CheckBox`/`OptionButton` for free via Godot's theme type inheritance (both extend `Button`), which is why the Shop roster's per-station checkboxes and routing-strategy dropdown pick up the same chunky look without their own theme entries.
- `TabContainer`'s own `panel` style is a **borderless** variant of the panel background (`StyleBoxFlat_tabcontainer_panel`) - giving it the same bordered style as the outer `Panel` would double up borders (outer frame + a second nested frame a few pixels in), so only the outer `Panel` actually draws a border; the `TabContainer` just contributes its tab-row styling and matching background fill.
- Breathing room came from two places, not just the theme: `VBoxContainer`/`HBoxContainer`/`GridContainer` separation constants are set theme-wide (8px/8px/10px+6px) so no popup needed per-node spacing tweaks, and the three overlay `.tscn` files each got their `Panel` and inner `Scroll`/`TabContainer` insets widened by hand (panel margins tightened from ~20px to ~10-15px screen edge, inner content inset doubled from 4px to 8px) since a plain `Panel` node doesn't auto-apply its stylebox's `content_margin` to children the way a `PanelContainer` would - only `TabContainer` (used for its `panel` style, which does drive layout) gets that padding for free.
- Section headers (Queue/Insert/Technician/Upgrade in the Station Detail Menu, Hire/Roster in the Shop overlay) and the Station Detail Menu's title get a manual per-node `theme_override_font_sizes`/`theme_override_colors` bump (18-20px, a dark rust accent color for headers) rather than a Theme type variation - type variations need a `base_type` declared inside the Theme resource itself with a serialization format that isn't well-documented for hand-authoring outside the editor, so per-node overrides were the safer choice here.
- **Font crispness bug fix:** the first time the project was opened in-editor, Godot auto-generated `assets/fonts/m5x7.ttf.import` with its normal TTF-oriented defaults (`antialiasing=1` grayscale, `hinting=3`, `subpixel_positioning=4`, `oversampling=0.0` auto) - fine for a body-text font, but it made the pixel font's edges visibly soft/"faded" rather than crisp, defeating the point of using a pixel font at all. Fixed by hand-editing that `.import` file to `antialiasing=0`, `hinting=0`, `subpixel_positioning=0`, `oversampling=1.0` (every glyph now rasterizes with no smoothing and snaps to whole pixels).
- **Font-breaks-when-zoomed-out bug fix:** the station Name/Status/TimerBar labels and the room name labels are drawn directly on the world-space `Node2D` floor - unlike the HUD/overlay text, which lives in a screen-space `CanvasLayer` and is never touched by the camera - so they get minified by `Camera2D` zoom same as every station sprite. That same `.import` pass above had left `generate_mipmaps=false` on the font, and minifying a mipmap-less glyph texture is exactly what produces visibly broken/garbled text rather than just soft text, since there's no downsampled mip level to sample from - fixed by setting `generate_mipmaps=true`. Generating mipmaps alone didn't do anything by itself, though, since whether they get *sampled* depends on the drawing node's own `texture_filter`, and the project's global default (`project.godot`'s `textures/canvas_textures/default_texture_filter=0`, Nearest) is deliberately plain-Nearest-no-mipmaps - correct for crisp pixel-art sprites, but exactly the setting that made mipmap generation alone insufficient for text. Fixed by setting `texture_filter` directly on the specific Control nodes affected instead of the project-wide default (which would've also pulled every sprite off crisp Nearest filtering) - `station.tscn`'s `NameLabel`/`StatusLabel`/`TimerBarLabel`, and the dynamically-created room label in `main.gd`'s `_add_room_zone()`. Went through `TEXTURE_FILTER_LINEAR_WITH_MIPMAPS` first, then settled on `TEXTURE_FILTER_NEAREST_WITH_MIPMAPS` - LINEAR avoids the aliasing bug too, but its interpolation between texels reads as blur on a pixel font even well within the still-legible zoom range, which is exactly the "still blurry" report that showed up after the aliasing was already fixed; NEAREST_WITH_MIPMAPS keeps hard pixel edges while still using a downsampled mip level instead of aliasing. `CanvasItem.texture_filter` isn't a themeable property, so this couldn't go in the shared `Theme` resource; it has to be set per-node.
- Both `.import` edits only change the recorded import params, not the cached binary at `.godot/imported/` - Godot reimports automatically on next editor focus/reopen in the normal case, but if either issue persists after that, trigger it manually via the FileSystem dock (right-click `m5x7.ttf` → Reimport).
- **Zoomed-out label readability, rebuilt from scratch this session (design request: "when you zoom out i cant tell what the stations are and what the text says unless i am extremely close up and i dont want the game to be played like that").** Two earlier approaches (documented in prior sessions, both now fully replaced) had already been tried and rejected: counter-scaling world-space labels bigger as zoom dropped (blurry - magnifying an already-small rasterized glyph via `Control.scale` doesn't add back detail that was never rasterized at that size - and neighboring stations' labels visibly overlapped at `MIN_ZOOM`), then hiding them below a hardcoded zoom threshold instead (`LABEL_HIDE_BELOW_ZOOM`, gone now) - legible while shown, but not shown at all past a fairly conservative cutoff, which is exactly what was reported as "can't tell what the stations are... unless extremely close up."
  - **The fix: station Name/Status labels and room name labels are no longer world-space children of the zoomable camera at all.** A new `FloorLabels` `CanvasLayer` in `main.tscn` (default `layer = 1`, positioned before `MenuOverlay`/`ShopOverlay` in tree order so it draws below any open overlay, per this session's z-order fix above) renders them in screen space instead - text is always drawn at native pixel-font resolution regardless of camera zoom, so it can never blur or need scaling math in the first place. `Station.name_label`/`status_label` (the original world-space `Label` nodes in `station.tscn`) are now always `visible = false` on the floor itself (set once in `main.gd._register_station()`) but keep being updated with exactly the same text by station.gd's existing, unchanged business logic (`_update_display()`, defect suffixes, etc.) - they're now just a pure data source, not something rendered directly. `main.gd._update_floor_labels()`, called every frame from `_process()` (not just on zoom-change events like the old system - screen position depends on pan too, not only zoom), mirrors that text into a screen-space `Label` per station (`_station_floor_labels`, one per real station id including printer instances) and one per room (`_room_floor_labels`, storing each room's fixed world anchor point since the room itself doesn't move but its *screen* position still needs recomputing every frame), positioning each via `get_viewport().get_canvas_transform() * world_position` - the standard Godot world-to-screen conversion, verified directly against a hand-computed expected value in a headless test.
  - **Overlap suppression, not a zoom cutoff, is what decides visibility now.** `_place_and_maybe_show_label()` computes each label's on-screen content rect (`Label.get_minimum_size()`) and shows it only if it's actually on-screen AND doesn't intersect any rect already accepted this frame - processed rooms first (so the handful of room labels always win any contest, spread out enough across the floor that they rarely collide with each other either), then stations in stable dictionary-insertion order. This means a fully-zoomed-out view now legitimately shows *some* station labels (whichever fit without colliding) instead of hiding all of them past one fixed threshold - verified with a headless test: at `MIN_ZOOM`, several station labels were suppressed (confirming the overlap logic actually engages when the floor is fully zoomed out) while several others stayed visible and provably didn't collide with each other (no two visible labels closer than 4px on screen).
  - Station labels are a combined two-line `"%s\n%s"` (name + status) rather than two separately-positioned Controls, both for a simpler single-rect overlap check and so a station's name never shows without its status or vice versa. Styled with white text and a black outline (`font_outline_color`/`outline_size` theme overrides) rather than the shared UI theme's default dark-on-parchment look, specifically because these now render over arbitrary, unpredictable floor content (room fill colors, station sprites) instead of one of the theme's own panels - a fixed dark color would disappear against a dark room palette.
  - The timer bar and its embedded countdown text (`TimerBarLabel`) are unchanged, still world-space and shrinking with zoom - deliberately out of scope, matching what the *old* zoom-visibility toggle already only ever applied to Name/Status, not the timer bar either. Station sprite silhouettes and click targets are also untouched.
  - Placeholder art for the 8 stations without real sprites (still just a tinted bordered box, not visually distinct per station) was explicitly scoped OUT of this session's fix per direct instruction ("just fix the text for now") - "can't tell what the stations are" from silhouette alone is still an open gap, this session only fixed the text-legibility half of that complaint.
- **Shelling Tier 2+ parallel independent timers (design doc Section 21.4, this session).** Tier 1 Shelling is unchanged - single part, one combined `station_timer`. At `current_tier >= 2` (`Station.is_parallel_shelling()`), the station switches to a genuinely different runtime model: `Station.shelling_active_parts: Array[ShellingRun]` (a small inner class - `part`, `elapsed`, `duration`) holds up to `batch_cap` Parts each running their own independent clock, ticked directly in `_process_parallel_shelling()` rather than through the shared `station_timer` node every other station uses. `batch_cap` is repurposed here as "how many parallel runs at once" (`GameData.SHELLING_TIER_PARALLEL_CAP`, a first-pass placeholder, +1 slot per tier from Tier 2) rather than a shared-batch-timer size. Finished runs move into `shelling_ready_parts` (the parallel equivalent of a single `current_part` sitting `READY`, except several can be ready at once). Every generic Station method that used to assume a single `current_part` (`can_accept_part()`, `receive_part()`, `collect_ready_part()`, `_try_send_to_next_station()`, `has_actionable_work()`, `_update_display()`, `get_overview_status()`, `_defect_suffix()`) now branches on `is_parallel_shelling()` via two shared predicates, `_has_ready_part_to_send()` and `_has_open_slot_to_fill()`, so the exact same script serves both models without duplicating the class - verified these predicates are equivalent to the old `current_state==READY`/`current_state==IDLE` checks for every non-parallel station, so nothing else changed behavior. Defect rolling, familiarity, technician carry/deposit, and the queue rack all reuse their existing generic logic unchanged - only the "how does a Part actually get from queued to ready" clock model is different. **One-time migration:** upgrading Shelling from Tier 1 to Tier 2 while a Part is already mid-run under the old `station_timer` wraps its remaining time into a `ShellingRun` (`_migrate_to_parallel_shelling()`) rather than leaving it stuck - called from `_apply_tier_batch_effects()`. The Station Detail Menu's defect row (`_refresh_defect_row()`) lists fix buttons for every flagged Part across `shelling_active_parts`/`shelling_ready_parts` for a parallel-shelling station, not just one. **Known rough edge:** `Technician._priority_tier_for()`'s routing-priority heuristic still treats a station as "actionable while idle" only via `current_state == IDLE`, so a parallel-shelling station that's partially busy (some slots running, one still open) won't be prioritized by a technician deciding where to walk next among several assigned stations - once they do arrive (for any other reason), the open slot still gets filled correctly, this only affects route-planning preference, not correctness.
- Not done: `CheckBox`'s own check-icon glyphs and `SpinBox`'s increment/decrement arrows still use Godot's built-in default icons (no custom pixel art asset for those yet).
- **Horizontal scrollbar removed, text wraps instead (this session):** every `ScrollContainer` across the three overlays (`menu_overlay.tscn`, `shop_overlay.tscn`, `station_detail_menu.tscn`) now sets `horizontal_scroll_mode = 0` (disabled) - Godot clamps a `ScrollContainer`'s child to its own width on whichever axis scrolling is off, which is what makes wrapping possible at all rather than the child just growing wider and needing to be scrolled to read. That alone isn't enough on its own, though: every `Label` (static ones in the three `.tscn` files, and every dynamically-created `Label.new()` across `menu_overlay.gd`/`shop_overlay.gd`/`station_detail_menu.gd`) also needed `autowrap_mode` set (`3`, `AUTOWRAP_WORD_SMART`, in code and in `.tscn`) - without it, a `Label` reports its full unwrapped line as its minimum size regardless of the container clamp, so it would've just been silently clipped instead of wrapping. Row `Label`s that already had a `custom_minimum_size` (e.g. the 160-180px info columns in the Hire/Roster/Queue/Insert rows) keep that as their wrap width once autowrap is on, rather than needing a separate `size_flags_horizontal` change.

**Stations** (`scenes/station.gd` + `scenes/station.tscn`)
- One reusable, data-driven `Station` scene covers every station from the design doc's Station Mechanics table, configured via exported properties rather than one separate scene per station. **Revised this session per design doc Section 21.3-21.5:** Deplate is gone entirely - collecting a finished pattern off a printer *is* the deplate action now, no separate station, timer, or player action. Clean, Patching, and Mold Prep are new. The real pipeline sequence (`GameData.PIPELINE_ORDER`) is now Printing -> Clean -> UV Cure -> Structured Light Scan -> Patching -> Pour Cup Attach -> Shelling -> Burnout -> Mold Prep -> Pour -> Deshell -> Abrasive Blast -> Ship. Clean (Print Room, batched, no defect risk) removes excess resin right after collecting off a printer, before UV Cure - moved ahead of Scan specifically so resin residue can't throw off the structured light reading. Patching (Print Room, single-part, not batched) sits after Scan, before Shelling: every part passes through it, not just flagged ones - see the "Patching auto-resolve" bullet under Quality, Defects, and Geometry Familiarity below for its auto-resolve behavior, which is also the actual mechanism behind "no player decline option in the Print Room" (design doc Section 21.6). Mold Prep (Furnace Room, single-part, not batched) sits after Burnout, before Pour, and is now specifically where Mortar Patch happens (see below), no longer a free-floating fix-it action available from anywhere.
- **Printing reworked into multiple independently-tiered purchasable printer instances, capped by factory level (design doc Section 21.2, this session).** There's no longer one shared Printing `Station` - `main.gd` spawns one live `Station` instance per `GameData.owned_printer_count` (starts at 1, same as every save always had exactly one printer before this), ids `"printing_1"`, `"printing_2"`, etc., each independently tiered exactly like any other station (`current_tier` already lived per-instance, nothing new needed there). `GameData.buy_printer()` spends `GameData.printer_purchase_cost()` (a new first-pass placeholder cost curve, `PRINTER_PURCHASE_COST`) and is capped by `GameData.printer_cap()` (`FACTORY_LEVEL_PRINTER_CAP`, only Level 1 -> 2 populated per the doc's own example - what actually raises `factory_level` isn't specified anywhere in Section 21, so nothing raises it yet, it just sits at 1). Buying a printer emits `printer_purchased`, which `main.gd` listens for to spawn the new instance live rather than requiring a reload - it also re-wires every printer's `next_station` to Clean (`_wire_next_station_links()`) and applies the current camera zoom's sprite scale/label visibility to the new instance immediately. Bought from a new **Printers** tab on the Shop overlay (a simple status line plus one Buy button, same spirit as the Specialists tab - individual printer tiers/rack capacity are still managed per-instance from that printer's own Station Detail Menu, same Upgrade/Upgrade Rack buttons every station has). Each printer's own tier now genuinely gates its batching (`GameData.PRINTER_TIER_BATCH_CAP`, a first-pass placeholder table since the doc gives no concrete tier thresholds - unbatched through Tier 2, batching unlocks Tier 3+) via `Station._apply_tier_batch_effects()`, called from `try_upgrade()`. `GameData.PIPELINE_ORDER`'s own `"printing"` entry is now a placeholder only used for `Part.current_station_index` arithmetic and as the shared Tier-1 template (`GameData.get_station()` falls back to it for any `"printing_N"` id) - no live Station node ever actually has `station_id == "printing"`. Anywhere UI needs to walk every real station (the Shop's technician-assignment checkboxes, the Menu Overlay's Overview tab) now uses the new `GameData.all_real_station_ids()` helper instead of iterating `PIPELINE_ORDER` directly, since that would silently skip every printer instance. Each printer instance's on-floor label uses its own `station_name` (`"Printing #2"`, etc., set at spawn) rather than the shared `StationDef.display_name`, so the floor, Station Detail Menu, Shop roster checkboxes, and any "currently at/walking to" text can all actually tell printers apart - `_display_name_for()` in both `ShopOverlay` and `StationDetailMenu` now prefers the live Station's own name over the StationDef lookup for this reason. Printers spawn in their own row in the Print Room (`main.gd._printer_position()`, a formula rather than one fixed position per id, since the owned count is a runtime purchase).
- Three station types: `QUEUE`, `BATCHED`, `AUTOMATIC` (Ship only).
- Tier 1 timer/batch numbers for every station loaded from `GameData`, converted from the design doc's real minutes to prototype-scale seconds (real minutes × 1/3, e.g. 15 real minutes → 5s), floored at a 2s minimum.
- Sprite swapping by `current_tier`: Printing has all 5 real tier sprites wired; Burnout and Pour each reuse their one sprite across all 5 tier slots (no tiered art generated yet); the other 8 stations fall back to a generated placeholder tinted by state (white/yellow/green for idle/running/ready). `current_tier` can now be raised by the player (see Station Detail Menu below), but the sprite swap is the only real effect so far - upgrading doesn't shorten `timer_duration` or raise `batch_cap` yet even though it charges currency for it.
- **Clean now has real per-state art with an interaction animation, the first station to move past the generic placeholder (design request, this session: "use those cleaner images and attempt to make it an animation that plays when a technician interacts with the station").** `Station.state_sprites: Array[Texture2D]` (new, `station.gd`) is a second art system alongside `tier_sprites` - indexed by `current_state`-adjacent logic instead of by tier, since a single station can't represent both an upgrade tier AND a running-state photo with the same static image. `GameData.CLEAN_STATE_SPRITES` (`cleaner_1/2/3.png` - closed, open/basket-submerged, open/basket-lifted) is passed through a new `StationDef.state_sprite_paths` constructor arg, loaded into `state_sprites` by `main.gd._instantiate_station()` exactly the way `tier_sprite_paths` already was. `Station._update_sprite()` checks `_has_state_art` (`state_sprites.size() >= 3`) before falling through to the existing tiered-art/placeholder logic, and `_update_display()`'s two state-tint call sites were unified into one `_refresh_state_visual()` that picks whichever of the three art systems this station actually has.
  - **Two bug fixes on top of the first pass, same session, from direct feedback on a screenshot.** (1) "it should be closed when the technician leaves the station": `_apply_state_sprite()` originally mapped IDLE/RUNNING/READY to closed/open-submerged/open-lifted respectively, which read as the lid being left open unattended while the machine ran on its own - like a dishwasher running with the door open. Fixed by making `state_sprites[0]` (closed) the permanent default in every one of IDLE/RUNNING/READY - the open frames (`state_sprites[1]`/`[2]`) now ONLY ever appear during the interaction flourish itself, while a technician is physically mid-interaction, never as a sustained state indicator. (2) "the cleaner is a bit larger than the rest": `cleaner_1/2/3.png` are 1254x1254, the same resolution class as Burnout/Pour's real art - fine for them since each gets a whole room mostly to itself, but Clean sits packed into a tight row with UV Cure/Scan/Patching's small placeholder boxes, where the same on-screen size visibly dwarfed its neighbors. Fixed with a new general per-station fudge factor, `Station.sprite_scale_override` (multiplies `BASE_SPRITE_SCALE` in both `_ready()` and `set_sprite_scale_multiplier()`, threaded through via a new `StationDef.sprite_scale_override` constructor arg) - `GameData.CLEAN_SPRITE_SCALE_OVERRIDE` (0.35) shrinks Clean down to roughly match Printing's own on-screen size; every other station stays at the default 1.0 (no change).
  - **The interaction animation itself**: while `active_worker != null and active_worker.is_interacting` (the existing ~1.5s `Technician.INTERACT_SECONDS` pause a technician already does after physically loading/collecting a part - no new Technician-side state needed), `Station._process()` advances a local `_interact_anim_elapsed` and `_apply_state_sprite()` cycles through all 3 `state_sprites` frames at 0.5s each - 3 frames × 0.5s lands exactly on the last frame as the interaction ends, so the flourish always completes cleanly rather than being cut off, then falls back to closed the very next frame once `is_interacting` goes false. The same mipmap/`NEAREST_WITH_MIPMAPS` fix as every other real station sprite was applied to the 3 new `.import` files (see the pixelation fix below - same convention). Verified with headless tests: each abstract state (IDLE/RUNNING/READY) now shows closed by default, the flourish still correctly shows frames 0/1/2 at t=0.1/0.6/1.1s into a simulated interaction, it correctly reverts to closed the instant the interaction ends (technician leaves or `active_worker` clears), and Clean's on-screen scale now roughly matches Printing's instead of Burnout/Pour's.
- **Placeholder size bug fix (this session):** the 8 stations without real art rendered as a bare 64x64 white square (`Station._get_placeholder_texture()`) - at `BASE_SPRITE_SCALE` (0.18) that's an ~11px dot on screen, effectively invisible next to Burnout/Pour's real ~1254px photo assets rendering at the same scale (~225px), reported as "can barely see any of the pictures of machines." - **Station/technician sprite pixelation-when-zoomed-out fix (this session, art follow-up to the earlier text-legibility pass): "i just really dont like how pixelated it gets when im zoomed slightly out."** Root cause was the same shape as the earlier font mipmap bug, just never applied to sprites: at `MIN_ZOOM` (0.25) a world-space sprite gets minified onto far fewer of the fixed 480x270 canvas's pixels before the whole canvas is stretched up to the real device resolution, and with no mipmaps and plain Nearest filtering, that minification aliases into visible blockiness rather than a clean downsample.   1. Skip the candidate entirely if `station.active_worker` already belongs to someone else - it's already being handled.
  2. Otherwise, skip it if `GameData.closest_assigned_technician_distance(station_id, excluding_self)` finds ANY other technician assigned there - cargo-carrying or not - physically closer right now than this technician is.

- `Camera2D` freely pannable (click-drag / touch-drag) and zoomable (mouse wheel / pinch gesture, 0.25x-2.0x), clamped to the floor's bounds so you can't drag or zoom past the edges. `_pan_camera()` deliberately does NOT scale by `camera.zoom` - a given drag distance moves the camera through the same world-space distance at any zoom level, which is what felt right after the "textbook" `screen_delta * zoom` (1:1 cursor tracking) made drag speed feel zoom-dependent.
- **Zoom direction, gotten backwards once and fixed:** in Godot, a HIGHER `Camera2D.zoom` value means MORE magnified (LESS world area visible), not more area - confirmed directly against `Camera2D.get_canvas_transform()`. `MIN_ZOOM` (0.25 - low enough that the entire 1720x960 floor fits on screen at once, rather than just "most of" it) is zoomed out, `MAX_ZOOM` (2.0) is zoomed in. `_clamp_camera_position()`'s `half_view` is `VIEWPORT_SIZE * 0.5 / camera.zoom` (divide, not multiply) - the earlier multiply-based version had the clamp range backwards, which is what made stations near the floor edges genuinely unreachable while zoomed in (verified: at the reported bug state, Printing's real screen position was off-window at x=-360). Mouse wheel up and pinch-out now increase the zoom value (zoom in), matching normal convention.
- **Zoom now anchors to the cursor/pinch position, not the screen center (this session).** Previously `_zoom_camera()` only changed `camera.zoom` and re-clamped `camera.position` - since position never moved to compensate, zooming in always converged on the middle of the screen no matter where the mouse was, which felt wrong when zooming in on an off-center station. `_zoom_camera(factor, anchor_screen_pos)` now takes the screen position to zoom toward (the mouse's `InputEventMouseButton.position` for a wheel scroll, the gesture's own `InputEventMagnifyGesture.position` for a pinch) and applies the standard zoom-to-point trick: compute which world point currently sits under that screen position *before* changing zoom, then shift `camera.position` by however much that same screen position's world point moved *after* changing zoom, so the point that was under the cursor stays under the cursor. Computed directly from `camera.position`/`camera.zoom` and `VIEWPORT_SIZE` (the same `half_view` relationship `_clamp_camera_position()` already uses) rather than via `get_global_mouse_position()`, since that depends on the `Camera2D`'s own canvas transform having already updated for the new zoom within the same frame, which isn't guaranteed.
- `_apply_sprite_zoom_scale()` in `main.gd` shrinks station sprites toward `MAX_ZOOM_SPRITE_SCALE` (0.75x) as zoom approaches `MAX_ZOOM`, full size at `DEFAULT_ZOOM` and below - `Station.set_sprite_scale_multiplier()` applies it, and `get_click_rect()` reads the sprite's live scale so the clickable area shrinks in step with the sprite.
- **Real mobile pinch-to-zoom bug fix (this session): "when i remote deploy the game on my phone i cant zoom."** The only pinch handling that existed was `InputEventMagnifyGesture`, which Godot synthesizes exclusively from a desktop trackpad's own native gesture recognizer (e.g. macOS) - a real touchscreen never generates that event at all, so pinch-zoom silently never worked on an actual phone export even though wheel-zoom (and, if ever tested that way, a desktop trackpad) both worked fine. Fixed by tracking real per-finger touch state directly: `_touch_points: Dictionary` (touch index -> last position), updated from `InputEventScreenTouch` (`_on_screen_touch()`) and `InputEventScreenDrag` (`_on_screen_drag()`), which are the actual events a touchscreen sends. With exactly one finger down, `_on_screen_drag()` pans exactly as before (`_pan_camera()`); with two, it computes the ratio between the current and previous inter-finger distance (`_pinch_distance()`) and feeds that straight into the existing `_zoom_camera(factor, anchor)` - same zoom-to-point math a wheel tick or trackpad gesture already uses, anchored to the midpoint between the two fingers (`_pinch_midpoint()`) instead of the screen center. **Bug this also had to guard against:** a second finger touching down while `_dragging` was still `true` from the first finger's initial press would otherwise fight the pinch, since Godot's mouse-motion emulation keeps tracking whichever finger drives its emulated pointer even with a second finger also down - `_on_screen_touch()` clears `_dragging` the moment a second touch point appears, so the pinch's own camera repositioning isn't also being panned by the stale single-finger drag state. Verified with a headless test driving synthetic `InputEventScreenTouch`/`InputEventScreenDrag` events directly through `_unhandled_input()`: two fingers spreading apart zoomed in, pinching back together zoomed back out, lifting one finger correctly ended the pinch (`_pinch_last_distance` reset to 0), and the remaining single finger correctly resumed panning (zoom unchanged, camera position moved) rather than continuing to zoom.
